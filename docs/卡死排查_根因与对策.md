# 整机突然卡死（需重启）：根因分析与对策

> 症状：工厂环境下电脑**整机**突然卡死，只能硬重启，重启后无证据留存。
>
> 本文回答两个具体假设，再给出完整的可能因素清单和已落地的修复。
> 所有数字都是在本仓库里实测/复算出来的，标注了出处；
> 无法在仓库内验证的一律单独列在"需现场确认"里。

---

## 一、先回答两个假设

### 假设 A：硬触发过快导致卡死？—— **不成立**

触发是**距离驱动**的，且被主循环轮询频率硬顶住，不可能失控变快。三个独立的闸门：

| 闸门 | 出处 | 值 |
|---|---|---|
| 主循环轮询间隔 | `config.yaml → plc.read_interval_ms` | 100 ms → **上限 10 Hz** |
| 触发距离 | `102 × scaling_factor(0.78651)` | **80.22 mm** |
| 每拍最多一次 | `Modbus.py::MotionController.update()` 用的是 `if` 而不是 `while` | 一拍 1 次 |

按真实参数复算的每相机帧率：

| 织机速度 | 理论帧率 | 实际（被 100ms 轮询封顶） |
|---|---|---|
| 1 m/min | 0.21 fps | 0.21 fps |
| 10 m/min | 2.08 fps | 2.08 fps |
| 20 m/min | 4.16 fps | 4.16 fps |
| 40 m/min | 8.31 fps | 8.31 fps |
| **60 m/min** | 12.47 fps | **10.00 fps（欠账，少拍）** |

`update()` 里的关键代码：

```python
if self.accumulated_distance >= self.config.trigger_distance:
    should_trigger = True
    self.accumulated_distance -= self.config.trigger_distance   # 只扣一次
    self.trigger_count += 1
```

因为是 `if` 不是 `while`，**一拍之内无论累计距离超出多少个 trigger_distance，都只发一次触发**，
多出来的留在 `accumulated_distance` 里。所以速度越高，系统是**少拍**（欠账），而不是多拍。

> 结论：触发速率有硬上限，不可能"过快"。
> 真正的量级问题是**聚合带宽**：8 台相机 × 10 Hz = 80 fps，
> 2440×2048 BGR 单帧 14.3 MB，聚合 **1.12 GB/s** 的数据要穿过 Python 进程。
> 这是负载问题，不是失控问题 —— 靠丢帧策略和内存上限兜，不是靠降触发频率。

已由 `Test_Tool/test_motion_controller.py` 的
`test_at_most_one_trigger_per_tick_even_if_distance_runs_far_ahead` 和
`test_trigger_rate_is_capped_by_poll_interval` 两条用例守住。

### 假设 B：经纬线分析太频繁导致卡死？—— **不成立（已有界）**

经纬分析有**四道**独立的限流，不可能无限积压：

| 限流 | 出处 | 值 |
|---|---|---|
| 采样间隔 | `config.yaml → concurrency.warp/weft_sample_interval` | 每 **2** 帧一次 |
| 在飞任务数 | `detection_pipeline.py` 的 `_warp_cache.try_mark_inflight()` | 每条 pipeline **1** 个 |
| 纬线队列深度 | `detection_pipeline.py::WEFT_MAX_QUEUE_DEPTH` | 全局 **4** |
| 线程数 | `concurrency.warp_workers` / `weft_workers` | 各 **2** |

另外 `CAMERAS_WITHOUT_WEFT = {"camera1", "camera8"}` 直接排除了 2 台相机。

我还专门核了 `SharedFrame` 的引用计数有没有漏放（漏一次就多留一份 14.3MB）：

| acquire 点 | 对应 release 点 | 是否在 `finally` |
|---|---|---|
| `detection_pipeline.py:471`（经线） | `:581` | ✅ |
| `detection_pipeline.py:530`（纬线） | `:607` | ✅ |
| 主链路 `owner_release()` | `:377` | ❌ **当时不在，已在 `e01280f` 补上** |

> 行号以本次提交为准（`_init_stats()` 新增 2 个计数键使 358/375 下移到 360/377；
> 经纬线提交处的回滚改动使 459/491/526/552 移到 471/530/581/607）。

> **订正**：本表第三行最初标的是 ✅，那是错的。主链路的 `shared.owner_release()`
> 当时是**裸调用**，紧跟在 `self._submit_analysis_tasks(...)` 后面，没有 `finally`
> 保护。而 `_submit_analysis_tasks` 内部是**先 `shared.acquire()` 再
> `executor.submit()`**，一旦 acquire 之后抛异常（线程池已 shutdown 等），
> `owner_release()` 就永远执行不到，`_ref_count` 停在 ≥1，`_image` 不会被置空。
>
> 同时订正我当时给出的严重性判断。我说过这会"泄漏 14.3 MB/帧"，**这个说法过重了**。
> 用 `weakref` 实测四种场景后的结果：
>
> | 场景 | 图像是否被 GC | `_image` 是否置空 | 残留 refcount |
> |---|---|---|---|
> | 正常，无后台任务 | True | True | 0 |
> | 正常，1 个后台任务已完成 | True | True | 0 |
> | 异常，`owner_release` 未调用 | **True** | False | 1 |
> | 异常，已 acquire 未 release | **True** | False | 2 |
>
> 关键在倒数两行的 `图像是否被 GC = True`：`detect()` 返回后 `shared` 随局部变量
> 出栈，CPython 会把 `SharedFrame` 和它持有的数组一起回收，**不构成永久泄漏**。
> 真正的风险窄得多——异常传播路径上 traceback 会持有帧的局部变量，只要异常对象被
> 留存（日志 `exc_info`、`sys.last_traceback`、上层 `except` 里存了引用），这一帧的
> 14.3 MB 就会跟着 traceback 滞留。属于"值得修但不紧急"，不是卡死主因。
>
> 已在 `detection_pipeline.py:360-377` 用 `try/finally` 包住，确定性断开引用。

> 结论：经纬分析确实重（`weft_skew_analyzer.py` 1039 行 numpy），
> 但**频率有闸、积压有上限**，不会自己把内存吃爆。
> 它的影响是 CPU/GIL 争用，会让采集线程变慢，而不是让整机卡死。

## 二、真正找到的问题（按危害排序）

### 1. 每条日志都跑一次 `inspect.stack()` —— 已修

`General_Tool/EnhancedLogger.py::_get_caller_info()` 原实现在**每一条**日志上调用
`inspect.stack()`，而且发生在级别判断**之前**。

实测对比（本机基准）：

| 栈深 | 原 `inspect.stack()` | 改后 `sys._getframe()` | 提升 |
|---|---|---|---|
| 10 帧 | 266 µs | 1.75 µs | **152×** |
| 25 帧 | 597 µs | 2.35 µs | **255×** |
| 参考：logging 自带 `findCaller` | 0.8 µs | — | — |

慢的根本原因：`inspect.stack()` 会对**每一帧**调 `getframeinfo()`，
后者要经 `linecache` 把源文件对应行读出来。本项目
`detect_image → pipeline → tasks` 嵌套 25 帧以上，正好踩在最慢的区间。

叠加放大系数：`config.yaml` 里 `logging.level` 原本是 **DEBUG**，
相机回调热路径上还有每帧一条 `debug(f"[原始回调] ...")`，
8 台相机 × 10 Hz = **80 条/秒起步**，且跑在 SDK 采集线程上。

顺带修掉一个潜在崩溃：原实现的"备用方案"分支引用了 `stack` 变量，
但若 `inspect.stack()` 自身抛错，`stack` 根本没被绑定 → `NameError`；
而那个 `except` 只捕获 `IndexError/AttributeError`，`NameError` 会直接漏出去。

**修复**：改用 `sys._getframe()` 手工回溯（不读源文件）+ 级别预检前置；
删掉回调里每帧的 `debug()`；`logging.level` 改为 `INFO`。

### 2. 编码器计数突变无任何防护 —— 已修

`MotionController.update()` 里 `pulse_delta = hc0 - self.last_hc0` 直接用。
PLC 的 HC0 计数器**被复位、断电回零、或 32 位回绕**时，这个差值会瞬间变成天文数字。
实测注入一次回绕：

```
[编码器] HC0 计数突变：last=6811 -> now=2147483647 (Δ=2147476836 脉冲,
折算速度 30,353,439 m/min 超过上限 300 m/min)
```

后果有两个，都极难排查：

1. `current_speed` 变成天文数字 → 永远高于 `idle_speed_threshold(0.5 m/min)`
   → **`is_idle` 永久为 False** → 停机预览模式再也进不去，软触发预览彻底失效；
2. `accumulated_distance` 被灌进巨大值，触发节拍错乱。

**修复**：按本拍时长折算成速度，超过 `max_plausible_speed_mpm`（默认 300 m/min，
织机实际线速度远低于此）就判为突变 —— 丢弃本拍、重新对齐基准、保持突变前的状态值。
由 `test_counter_reset_to_zero_is_discarded` / `test_counter_wrap_to_huge_value_is_discarded` /
`test_glitch_does_not_break_idle_detection` / `test_small_counter_jump_within_plausible_range_is_kept`
四条用例守住（最后一条防止把织机轻微倒车误杀）。

### 3. 卡死时零证据 —— 已修

`config.yaml → logging.faulthandler_dump_after` 原本是 **0（关闭）**。
也就是说每次卡死，`crash.log` 里什么都没有。

`faulthandler.dump_traceback_later` 的转储线程跑在 **C 层、自带定时器、不需要 GIL**，
所以即使所有 Python 线程都死锁在 GIL 上，它照样能把各线程的栈打出来 ——
这正是排查"整机卡死"最需要的手段。

原代码还有个隐患：`open()` 的结果是个临时对象，没有引用、没有 `try` 保护，
磁盘满/权限问题时**直接掀掉整个进程启动**，且句柄一直不关。

**修复**：默认开启（60s 一次）；`open()` 加 `try` 保护并存到模块级变量；
退出时 `cancel_dump_traceback_later()` + 关闭句柄。

### 4. 没有健康心跳，渐进式故障无法取证 —— 已修

`faulthandler` 只能抓"某一瞬间卡在哪"，抓不到**内存一路涨到把页面文件打爆**
这类渐进式故障 —— 那需要的是**时间序列**。

**新增** `General_Tool/HealthMonitor.py`：每 30s 往日志写一行紧凑快照
（RSS / 峰值 RSS / 线程数 / CPU / 句柄数 / GC 计数 / 检测队列深度 / 各相机帧数与丢帧数），
超过 `health_rss_warn_mb` 或 `health_thread_warn` 自动升级为 WARNING。

卡死后翻最后几行心跳，可以直接分诊：

| 心跳表现 | 结论 | 往哪查 |
|---|---|---|
| RSS 一路爬升 | 内存泄漏 / 队列积压 | 上传链路、检测队列 |
| 线程数一路爬升 | 线程泄漏 | `ThreadPoolExecutor` / `Thread()` |
| `infer_q` 长期顶满 32 | 下游吞吐跟不上采集 | YOLO / GPU |
| `*.lost` 持续增长 | 网络丢包 | 带宽、巨型帧、网卡缓冲 |
| 心跳本身停了但进程还在 | 真·整机卡死 | 双网卡驱动 / 磁盘 / 系统层 |

### 5. 上一轮已修的 SDK 层问题（此处只列结论）

详见 `docs/SDK迁移_海康转大恒.md`：
`ctypes.py_object` 裸地址往返（解引用已释放内存，崩在 C 层无回溯）、
`ctypes.string_at(pData, w*h)` 按猜的长度读缓冲、
每帧白拷 15MB 的 `cv2.resize`、`MV_CC_SetImageNodeNum(1)`、
以及无人调用但极危险的 `Async_raise`/`Stop_thread` 强制杀线程。

### 6. 提交失败会让经纬线分析永久静默停摆 —— 已修

和上面第 1 节 `owner_release()` 是同一个形状的错误：**先预留资源，再把归还
责任交给一个可能根本不会运行的任务体**。

`_submit_analysis_tasks()` 里的顺序是：

```
try_mark_inflight()   → in_flight = True          （预留 1）
_weft_queue_depth += 1                            （预留 2，仅纬线）
shared.acquire()      → 引用计数 +1                （预留 3）
executor.submit(...)  ← 这里抛异常，任务体就永远不会运行
```

`reset_inflight()`、`_weft_queue_depth -= 1`、`shared.release()` 三处归还**全部
只写在任务体的 `finally` 里**。`submit()` 一旦抛异常（线程池已 shutdown、
`BrokenThreadPool`、起不了新线程），这三样都还不回来。

**代码里没有任何超时看门狗能把卡住的 `in_flight` 救回来**——我 grep 过
`in_flight` 的全部读写点，只有 `update()` 和 `reset_inflight()` 会清零，
而这两处都在任务体内部。

后果按作用域分级：

| 泄漏项 | 作用域 | 泄漏满之后的后果 |
|---|---|---|
| `_weft_queue_depth` | **模块级全局**，8 台相机共用，仅 **4** 个槽位 | 满 4 次后每帧都走 `depth_dropped` 直接 return，**全进程纬线分析永久停摆** |
| `_weft_cache.in_flight` | 每 pipeline 一份 | 该 pipeline 的纬线分析永久停摆 |
| `_warp_cache.in_flight` | 每 pipeline 一份 | 该 pipeline 的经线分析永久停摆 |
| `shared` 引用计数 | 单帧 | 多留一份 14.3MB，直到 `detect()` 返回被 GC |

纬线那一项最危险：只有 4 个槽位、全局共享。按 `config.yaml` 的 plc 参数算
（周长 3.141×60.0 = 188.46 mm，分辨率 2000×4 = 8000 脉冲/转，触发距离
102×0.78651 = 80.224 mm），10 m/min 下单相机 2.078 fps；扣除
`CAMERAS_WITHOUT_WEFT` 的 camera1/camera8 剩 6 台，再除以
`weft_sample_interval: 2`，全进程纬线提交速率约 **6.23 次/秒（374 次/分钟）**。

也就是说**一旦进入失败模式，4 个槽位在 0.64 秒内就被泄漏占满**，之后整机
纬线检测静默归零，而且不会有任何报错——`weft_task_depth_dropped` 会一直涨，
但那看起来像"限流生效"，不像故障。

修法：把预留到移交之间的窗口包进 `try/except`，失败时按相反顺序回滚，
并用 `acquired` 标志区分"`acquire()` 自己抛的"和"`acquire()` 成功、
`submit()` 抛的"——`SharedFrame.acquire()` 在 `_image` 为 None 时是在
`_ref_count += 1` **之前**抛的，那种情况不能再 `release()`，否则计数扣穿。

两个附带决定：

- `except BaseException` 但 `KeyboardInterrupt`/`SystemExit` **回滚后继续上抛**。
  吞掉它们会让 Ctrl+C 失灵。
- 普通 `Exception` 回滚后**不再上抛**。本帧的 YOLO 缺陷检测在 Step1/2 已经
  算完了，后台经纬线分析提交失败不该把这份结果一起丢掉。

新增两个计数并进 `async_analysis` 快照：`warp_submit_failed`、
`weft_submit_failed`；另外把 `warp_in_flight` / `weft_in_flight` 两个原始标志
也暴露出来。现场判读方法：

| 现象 | 含义 |
|---|---|
| `*_submit_failed` 一直涨 | 线程池出问题，分析在降级（但每次都已回滚，不会停摆） |
| `weft_queue_depth_now` 恒为 4 且 `weft_cache_updates` 不再增长 | 任务体卡住没收尾（典型是 CUDA 挂住），纬线已停摆 |
| `weft_in_flight` 恒为 True 且 `weft_submitted` 不再增长 | 同上，卡在任务体内部 |

回归测试：`Test_Tool/test_analysis_task_rollback.py`，12 例。已验证这 12 例
在修复前的代码上**全部失败**（`git stash` 掉改动后实测），不是空转的测试。

> 触发概率要如实说明：这个窗口只有 2~3 条语句宽，正常稳态跑不到。现实中的
> 触发源是**关机时序**（`atexit` 已 `shutdown` 线程池、检测线程还在收尾）、
> `BrokenThreadPool`、以及**起不了新线程**（这台机器本来就在卡死边缘，
> 线程耗尽是有可能的）。概率低，但后果是永久且无声的，而且**没有自愈路径**。

## 三、稳态内存预算（按 8 台 2440×2048 相机核算）

| 项 | 出处 | 占用 |
|---|---|---|
| YOLO 在途帧 | `yolo.max_inflight_frames: 12` | 172 MB |
| WebSocket 待推送（1 帧/相机） | `WebSocketImageServer._pending` | 114 MB |
| 布幅检测在途（1 帧/相机） | `main_yolo._fabric_pending` | 114 MB |
| 大恒 SDK 采集缓冲 | `buffer_count: 10 × 8` 台 | 381 MB |
| **合计** | | **≈ 0.76 GB** |

这个量本身不致命。但它是**在途下限**——一旦下游（YOLO/上传/磁盘）变慢，
在途帧数会顶到上限，再叠加 Python 侧的临时数组和 GC 压力就会往上走。
所以 `health_rss_warn_mb` 建议按**物理内存的一半**设置，提前报警而不是等卡死。

## 四、需现场确认的因素（我在仓库内无法验证）

按"最可能导致整机卡死"排序：

1. **网卡上是否同时装了海康和大恒两个 GigE 过滤驱动。**
   两个过滤驱动挂同一张网卡是"整机网络栈卡死"的高频原因。
   换 SDK 后请务必卸载/禁用海康 MVS 的 GigE Filter Driver，只留大恒的。
2. **物理内存与页面文件。** 上面 0.76GB 只是在途下限，YOLO+TensorRT+torch
   常驻还要数 GB。内存不足时 Windows 页面文件抖动会把整机拖到假死。
3. **磁盘。** `D:\yolo_detection_results` 写满会让所有 `imwrite` 阻塞。
   心跳里的句柄数异常也常是磁盘问题的前兆。
4. **巨型帧（Jumbo Frame）** 交换机与网卡必须同时开；只开一边会造成大量
   分片/丢包，CPU 被软中断打满。
5. **GPU 驱动 TDR / 显存耗尽。** 显存打满时 CUDA 调用可能长时间挂起。
6. **硬件层面**：电源、散热、内存条。整机需要硬重启（而不是进程能恢复）
   这一点本身就更偏向系统/硬件层，而不是纯应用层。
